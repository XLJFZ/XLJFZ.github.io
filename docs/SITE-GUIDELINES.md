# XLJFZ 摄影作品集维护规范

> 本文档是网站后续修改的约束清单。修改页面、添加照片或调整专题前，应先核对本文档，避免破坏已经确认的分类、排版、元数据和发布流程。

最后核对：2026-09-03

## 1. 网站定位与视觉基调

- 网站是 XLJFZ 的个人摄影作品集，不是通用图片瀑布流或社交相册。
- 视觉风格保持暖深灰、克制、留白充足、编辑式摄影画册感。
- 同源页面使用短暂、轻微的原生跨页淡入淡出；必须保留渐进增强，并服从系统“减少动态效果”设置。
- 桌面端内容最大宽度为 `1480px`，必须保留左右页边距，不能贴边。
- 移动端自然退化为单列，不保留桌面端的左右错落。
- 长专题的吸顶章节导航必须保持横向可滚动，并显示当前章节、总章节和克制的进度线；直接访问 `#chapter-N` 时，导航状态必须同步。
- 图片缩略图必须保留清晰的键盘焦点反馈，不能只依赖鼠标悬停效果。
- 不使用来源不明、AI 生成或非本人作品作为封面、分享图或装饰图。

## 2. 单一数据源与当前四个专题

所有专题、照片顺序、尺寸、说明、地点和年份都以 [`src/lib/portfolio.ts`](../src/lib/portfolio.ts) 为唯一数据源。

| 顺序 | 专题                          | Slug               | 定位                                 | 年份      | 地点                                     | 作品数 |
| ---- | ----------------------------- | ------------------ | ------------------------------------ | --------- | ---------------------------------------- | -----: |
| 01   | 城市脉冲 / Urban Pulse        | `urban-pulse`      | 城市、建筑、交通、街道与灯光         | 2022—2026 | 重庆、东京、上海、广州、深圳、南昌、香港 |     28 |
| 02   | 远方的天气 / Distant Weather  | `distant-weather`  | 山川、海岸、云雾、风与短暂光线       | 2024—2025 | 香格里拉、德钦、甘南、平潭、宁海         |      8 |
| 03   | 时间的纹理 / Textures of Time | `textures-of-time` | 历史空间、木构、民艺与时间留下的表面 | 2025—2026 | 大同、应县、景德镇、徽州、西安           |      7 |
| 04   | 近处发生 / Close at Hand      | `nearby-moments`   | 人物、动物与日常生活                 | 2023—2024 | 上海、西安                               |      2 |

分类原则：

- 城市建筑、交通、街头秩序优先进入「城市脉冲」。
- 自然地景和天气变化优先进入「远方的天气」。
- 历史建筑、传统文化、民间艺术和材料细节优先进入「时间的纹理」。
- 人物、动物和私人日常优先进入「近处发生」。
- 不要仅因新增一两张照片就随意创建第五个专题；只有题材明确独立且已有足够作品时再讨论新专题。

## 3. 照片排序与桌面端配对规则

画廊由 [`src/components/lightbox-gallery.tsx`](../src/components/lightbox-gallery.tsx) 统一渲染。

必须遵守：

1. 先按 `chapter` 分章节，同一地点或叙事段落不能跨章节配对。
2. 同一章节内优先把竖构图与竖构图、横构图与横构图配成一行。
3. 如果章节最后只剩一横一竖，则两张仍组成同一行，不能拆成左右错落的两行。南昌两张照片就是这一规则的基准案例。
4. 同行照片必须同顶线、同底线。通过轻微调整各自显示宽度实现等高，不能裁切照片。
5. `layout: 'wide'` 是明确的重点作品，应跨列独立展示，不参与普通配对。
6. 只有总数为奇数且没有可配对象时，才允许出现单张错落布局。
7. 禁止恢复“同行固定相同宽度”的旧做法；不同长宽比会因此造成底边不齐。
8. 禁止用人为的顶部外边距制造错落，这会破坏章节对齐。

当前实测基准：四个专题所有双列行的上下边缘误差均为 `0px`。

## 4. 移动端规则

- `md` 断点以下统一为单列，照片宽度服从可用内容宽度。
- 不在移动端强行保留桌面端等高宽度计算。
- 页面不能出现横向滚动条。
- 灯箱底部的 caption 与序号必须处于同一行并避免重叠。
- 触控左右滑动、键盘方向键和关闭按钮都必须保留。
- 灯箱黑色背景必须覆盖整个视口；图片自身保留呼吸空间。点击图片之外的黑色区域可关闭灯箱，点击图片与控制按钮不得误关闭。
- 灯箱底部可显示真实 EXIF，顺序固定为“机身 · 焦段 · 光圈 · 快门 · ISO”；视觉权重低于地点和年份。只显示文件中确认存在或由用户明确补充的字段，缺失项不得猜测。

## 5. 元数据与文字规则

- 拍摄时间只使用真实 EXIF `DateTimeOriginal` 或 `CreateDate`，绝对不能根据文件名猜测。
- 用户明确确认的地点或年份可作为权威补充；未确认的地点不要推断。
- 单张说明统一优先使用 `地点 · 年份`，例如 `徽州 · 2026`。
- 专题的 `year` 必须覆盖其中所有照片的真实年份；新增跨年作品后同步更新范围。
- 专题的 `location` 必须覆盖其中所有已确认地点。
- `width`、`height` 必须填写照片的真实像素尺寸，不能填写页面显示尺寸。
- `alt` 只描述画面中可见的内容，不虚构事件、身份或地理细节。
- 新文件使用稳定、可读的小写名称：`地点-相机或编号.jpg`。
- 加图前检查 `public/portfolio` 与 `src/lib/portfolio.ts`，避免重复加入此前的上海、西安或其他照片。

### 5.1 EXIF 证据与写入规范

灯箱 EXIF 的唯一写入位置是 `src/lib/portfolio.ts` 中对应照片记录的 `exif` 对象。网页用 JPEG 与生成的预览图可能已清除元数据，不能因此覆盖已核实的记录。

证据优先级：

1. 与网站作品明确对应的 RAW / DNG 原片。
2. 保留了完整元数据的导出图片。
3. 用户明确指定照片对应关系后提供的参数或截图。

必须先确认原片与网站文件的一对一关系，再写入数据。文件名、拍摄目录、相邻编号、相同镜头或同场景只能用于定位候选原片，不能单独作为填写某个 EXIF 字段的证据。

灯箱只允许以下五个字段，并按固定顺序显示：

| 字段           | 内容     | 格式示例                    |
| -------------- | -------- | --------------------------- |
| `camera`       | 机身     | `Nikon Z7 II`、`Sony α7 IV` |
| `focalLength`  | 实际焦距 | `26mm`、`9mm（等效 24mm）`  |
| `aperture`     | 光圈     | `f/2.8`、`f/8`              |
| `shutterSpeed` | 快门     | `1/500s`、`60s`、`900s`     |
| `iso`          | 感光度   | `ISO 64`、`ISO 12800`       |

- 相机型号可以规范化为公开产品名，例如 `NIKON Z 7_2` 写为 `Nikon Z7 II`、`ILCE-7M4` 写为 `Sony α7 IV`。无法唯一对应的内部型号不得自行改写；优先使用用户明确确认的展示名称。
- 焦距默认写实际焦距。只有原文件或用户明确提供等效焦距时，才在后面补充“等效”值。
- 不保存空字符串、`unknown` 或占位符。某个字段无法核实时直接省略，已核实的其他字段可以正常显示。
- 不向网站写入或展示 GPS、机身/镜头序列号、所有者信息、编辑历史、完整拍摄时刻等与灯箱展示无关或可能暴露隐私的元数据。
- 只读取核对所需的最少原片，不把 RAW / DNG、XMP 或用户的原始目录复制进网站仓库。
- 每次新增 EXIF 后，同步更新 `tests/portfolio-gallery.test.mjs` 中的 EXIF 记录总数和该照片的五字段断言，防止以后错配或意外删除。

## 6. 图片资产结构

```text
public/portfolio/                    原始展示照片；灯箱读取这里
public/portfolio/<series-slug>/      按专题保存原图
public/portfolio-previews/           画廊响应式预览，脚本生成
public/hero-previews/                首页主视觉响应式预览，脚本生成
public/covers/                       首页和专题索引使用的轻量封面
```

- 新增或替换原图后必须运行 `npm run previews`。
- 预览图由 [`scripts/generate-gallery-previews.mjs`](../scripts/generate-gallery-previews.mjs) 生成：宽度 `1200px` 与 `1800px` 两档、JPEG 质量 `90`、`4:4:4` 色度采样；列表优先使用预览图，灯箱才加载原图。
- 首页主视觉同时生成 `1280px` 与 `2200px` 两档预览，浏览器按屏幕宽度选择；移动端禁止直接下载 `3000px` 原图。
- 首页、专题索引与“下一组作品”的专题封面同时提供 `1200px` 移动版和高分辨率桌面版，必须通过 `srcset` 与 `sizes` 让浏览器按版面选择。
- 不要手工修改生成的预览图，也不要让画廊首屏直接下载全部原图。
- 长专题首章之后的屏幕外章节使用渐进增强的延迟绘制；必须保留章节锚点与不支持该能力的浏览器回退，不能通过卸载 DOM 破坏灯箱顺序。
- 章节高亮使用浏览器可见性观察器跟随章节标记，禁止恢复为滚动时持续读取全部章节位置的监听器。
- 灯箱继续加载原始展示照片，以保留放大观看质量。
- 灯箱先显示已缓存的 `1800px` 预览，再平滑切换到原图，避免黑屏闪烁；移动端控制按钮必须避开设备安全区域。
- 全局视口必须启用 `viewport-fit=cover`，让 iPhone 刘海屏和圆角安全区域样式真正生效；原图失败时保留高清预览，不显示空白。
- 专题封面建议为 `2400 × 1500`，并保持在 `1MB` 以内。

## 7. 站内照片工具

站内工具入口位于主导航“工具”，当前公开页面为 `/tools/image-compressor/`：

| 文件                                                                                    | 职责                               |
| --------------------------------------------------------------------------------------- | ---------------------------------- |
| [`src/app/tools/image-compressor/page.tsx`](../src/app/tools/image-compressor/page.tsx) | 页面元数据与工具布局               |
| [`src/components/image-compressor.tsx`](../src/components/image-compressor.tsx)         | 文件选择、压缩进度、预设与下载交互 |
| [`src/lib/jpeg-exif.ts`](../src/lib/jpeg-exif.ts)                                       | JPEG EXIF 检测与无压缩 ZIP 打包    |

### 7.1 照片批量压缩规则

- 工具只接受 JPG / JPEG，并允许一次选择或拖入多张照片；非 JPEG 文件必须明确忽略或报错，不能静默转换。
- 所有读取、压缩和打包都在浏览器本地完成，不把照片发送到网站服务器或第三方服务。
- 原文件不得覆盖。输出文件统一增加 `-web.jpg` 后缀，并以 ZIP 下载。
- 压缩内核使用 `compressorjs`，必须保持 `retainExif: true` 与方向校正，不能改回会清除 EXIF 的裸 Canvas 导出。
- 界面只提供三档，不重新引入连续质量滑杆：

| 档位 |   最长边 | JPEG 质量 | 用途               |
| ---- | -------: | --------: | ------------------ |
| 轻量 | `1600px` |      `76` | 文章配图与更快加载 |
| 推荐 | `2400px` |      `82` | 摄影网站默认选择   |
| 大图 | `3200px` |      `86` | 全屏查看与更高细节 |

- 如果原文件没有 EXIF，工具不得补造元数据；如果原文件有 EXIF，输出应继续保留。
- “保留 EXIF”包含原文件中可能存在的 GPS、序列号、所有者信息和完整拍摄时间。界面必须持续显示这一提醒，不能只写“保留拍摄参数”。
- 工具不会自动上传或提交输出文件。准备将结果放入公开仓库前，仍需按 5.1 节检查隐私；含 GPS 或序列号的文件不能因为经过压缩就被视为可安全公开。
- 本节描述的是下载文件内的元数据保留；作品灯箱仍只允许展示 5.1 节规定的五个字段，两者不能混为一谈。

### 7.2 工具路由与回归检查

- 新增站内工具时，必须同步更新主导航、`scripts/export-github-pages.mjs`、`public/sitemap.xml` 和对应测试。
- 照片压缩工具的基础约束由 `tests/image-compressor.test.mjs` 保护：本地处理、EXIF 保留、三档预设和无连续滑杆。
- `tests/navigation-links.test.mjs` 必须继续验证“工具”入口；`tests/github-pages-export.test.mjs` 必须继续验证工具页面被静态导出。
- 工具属于作品集的辅助能力，视觉上沿用暖深灰与编辑式排版，但首屏必须直接露出可操作区域，不能改成营销落地页。

## 8. 灯箱与链接行为

- 点击照片后，URL 使用 `?image=<image-key>`，以便复制和分享单张照片。
- 上一张、下一张只替换当前图片参数，不能不断堆积浏览器历史。
- 浏览器“返回”应关闭灯箱并保留当前章节锚点。
- 直接访问带 `?image=` 的链接时必须自动打开对应照片。
- 灯箱 caption 在左、作品序号在右，二者不能重叠。
- 邮箱与作品链接复制使用站内轻量状态提示并保留 `aria-live` 播报；禁止重新引入全局通知系统拖慢所有页面。

## 9. 新增照片的标准流程

1. 查看工作区状态，保留用户已有但与当前任务无关的修改。
2. 检查照片是否已经存在，并在任何缩放、压缩或重新导出之前，读取真实像素尺寸、EXIF 时间和灯箱需要的五个参数。
3. 建立原片/导出图与网站文件的明确对应；按 5.1 节的证据规则处理缺失字段和型号名称。
4. 根据本文件的分类原则确定专题；地点不确定时不猜。
5. 将经选择的高质量展示图复制到相应的 `public/portfolio/<series-slug>/`；不要复制 RAW / DNG 原片或旁车文件。
6. 在 `src/lib/portfolio.ts` 中添加记录与已核实的 `exif` 字段，并调整专题地点、年份和编辑顺序。
7. 为新照片增加 EXIF 映射测试，然后运行 `npm run previews` 生成所有响应式预览。
8. 在真实桌面视口检查同行顶边、底边和章节节奏；在手机视口检查单列和横向溢出，并在灯箱中核对 EXIF 顺序与文案。
9. 完成下方全部质量检查后才能提交。

## 10. 必须通过的质量检查

```bash
npm run lint
npm test
npm run build
npm run export:github-pages
git diff --check
```

检查重点：

- 所有照片都有对应的 `1200px` 与 `1800px` 预览图。
- 所有作品只被引用一次，没有重复照片。
- 专题年份覆盖真实照片年份。
- 首页、专题索引、详情页和 404 页面均能导出。
- 照片压缩工具仍保留三档预设、EXIF 保留和本地处理约束。
- 新增专题时必须同步更新 Pages 导出路由、`public/sitemap.xml` 和相关测试。
- 新增或修改工具时必须同步更新 Pages 导出路由、`public/sitemap.xml` 和相关测试。

## 11. GitHub Pages 发布

- 发布分支为 `main`。
- 推送后由 [`.github/workflows/pages.yml`](../.github/workflows/pages.yml) 自动部署。
- 不能只看到 `git push` 成功就宣布完成；必须确认对应 GitHub Actions 运行结果为 `success`。
- 部署完成后至少抽查受影响的公开页面，确认标题、照片和说明已经上线。
