# XLJFZ 摄影作品集维护规范

> 本文档是网站后续修改的约束清单。修改页面、添加照片或调整专题前，应先核对本文档，避免破坏已经确认的分类、排版、元数据和发布流程。

最后核对：2026-09-02

## 1. 网站定位与视觉基调

- 网站是 XLJFZ 的个人摄影作品集，不是通用图片瀑布流或社交相册。
- 视觉风格保持暖深灰、克制、留白充足、编辑式摄影画册感。
- 桌面端内容最大宽度为 `1480px`，必须保留左右页边距，不能贴边。
- 移动端自然退化为单列，不保留桌面端的左右错落。
- 不使用来源不明、AI 生成或非本人作品作为封面、分享图或装饰图。

## 2. 单一数据源与当前四个专题

所有专题、照片顺序、尺寸、说明、地点和年份都以 [`src/lib/portfolio.ts`](../src/lib/portfolio.ts) 为唯一数据源。

| 顺序 | 专题                          | Slug               | 定位                                 | 年份      | 地点                                     | 作品数 |
| ---- | ----------------------------- | ------------------ | ------------------------------------ | --------- | ---------------------------------------- | -----: |
| 01   | 城市脉冲 / Urban Pulse        | `urban-pulse`      | 城市、建筑、交通、街道与灯光         | 2022—2026 | 重庆、东京、上海、广州、深圳、南昌、香港 |     28 |
| 02   | 远方的天气 / Distant Weather  | `distant-weather`  | 山川、海岸、云雾、风与短暂光线       | 2024—2025 | 香格里拉、德钦、甘南、平潭、宁海         |      8 |
| 03   | 时间的纹理 / Textures of Time | `textures-of-time` | 历史空间、木构、民艺与时间留下的表面 | 2025—2026 | 大同、应县、景德镇、徽州、西安           |      7 |
| 04   | 近处发生 / Close at Hand      | `nearby-moments`   | 人物、动物与日常生活                 | 2023—2024 | 上海、西安                               |      2 |

分类原则：

- 城市建筑、交通、街头秩序优先进入「城市脉冲」。
- 自然地景和天气变化优先进入「远方的天气」。
- 历史建筑、传统文化、民间艺术和材料细节优先进入「时间的纹理」。
- 人物、动物和私人日常优先进入「近处发生」。
- 不要仅因新增一两张照片就随意创建第五个专题；只有题材明确独立且已有足够作品时再讨论新专题。

## 3. 照片排序与桌面端配对规则

画廊由 [`src/components/lightbox-gallery.tsx`](../src/components/lightbox-gallery.tsx) 统一渲染。

必须遵守：

1. 先按 `chapter` 分章节，同一地点或叙事段落不能跨章节配对。
2. 同一章节内优先把竖构图与竖构图、横构图与横构图配成一行。
3. 如果章节最后只剩一横一竖，则两张仍组成同一行，不能拆成左右错落的两行。南昌两张照片就是这一规则的基准案例。
4. 同行照片必须同顶线、同底线。通过轻微调整各自显示宽度实现等高，不能裁切照片。
5. `layout: 'wide'` 是明确的重点作品，应跨列独立展示，不参与普通配对。
6. 只有总数为奇数且没有可配对象时，才允许出现单张错落布局。
7. 禁止恢复“同行固定相同宽度”的旧做法；不同长宽比会因此造成底边不齐。
8. 禁止用人为的顶部外边距制造错落，这会破坏章节对齐。

当前实测基准：四个专题所有双列行的上下边缘误差均为 `0px`。

## 4. 移动端规则

- `md` 断点以下统一为单列，照片宽度服从可用内容宽度。
- 不在移动端强行保留桌面端等高宽度计算。
- 页面不能出现横向滚动条。
- 灯箱底部的 caption 与序号必须处于同一行并避免重叠。
- 触控左右滑动、键盘方向键和关闭按钮都必须保留。

## 5. 元数据与文字规则

- 拍摄时间只使用真实 EXIF `DateTimeOriginal` 或 `CreateDate`，绝对不能根据文件名猜测。
- 用户明确确认的地点或年份可作为权威补充；未确认的地点不要推断。
- 单张说明统一优先使用 `地点 · 年份`，例如 `徽州 · 2026`。
- 专题的 `year` 必须覆盖其中所有照片的真实年份；新增跨年作品后同步更新范围。
- 专题的 `location` 必须覆盖其中所有已确认地点。
- `width`、`height` 必须填写照片的真实像素尺寸，不能填写页面显示尺寸。
- `alt` 只描述画面中可见的内容，不虚构事件、身份或地理细节。
- 新文件使用稳定、可读的小写名称：`地点-相机或编号.jpg`。
- 加图前检查 `public/portfolio` 与 `src/lib/portfolio.ts`，避免重复加入此前的上海、西安或其他照片。

## 6. 图片资产结构

```text
public/portfolio/                    原始展示照片；灯箱读取这里
public/portfolio/<series-slug>/      按专题保存原图
public/portfolio-previews/           画廊响应式预览，脚本生成
public/covers/                       首页和专题索引使用的轻量封面
```

- 新增或替换原图后必须运行 `npm run previews`。
- 预览图由 [`scripts/generate-gallery-previews.mjs`](../scripts/generate-gallery-previews.mjs) 生成：宽度 `1200px` 与 `1800px` 两档、JPEG 质量 `90`、`4:4:4` 色度采样；列表优先使用预览图，灯箱才加载原图。
- 不要手工修改生成的预览图，也不要让画廊首屏直接下载全部原图。
- 灯箱继续加载原始展示照片，以保留放大观看质量。
- 灯箱先显示已缓存的 `1800px` 预览，再平滑切换到原图，避免黑屏闪烁；移动端控制按钮必须避开设备安全区域。
- 专题封面建议为 `2400 × 1500`，并保持在 `1MB` 以内。

## 7. 灯箱与链接行为

- 点击照片后，URL 使用 `?image=<image-key>`，以便复制和分享单张照片。
- 上一张、下一张只替换当前图片参数，不能不断堆积浏览器历史。
- 浏览器“返回”应关闭灯箱并保留当前章节锚点。
- 直接访问带 `?image=` 的链接时必须自动打开对应照片。
- 灯箱 caption 在左、作品序号在右，二者不能重叠。

## 8. 新增照片的标准流程

1. 查看工作区状态，保留用户已有但与当前任务无关的修改。
2. 检查照片是否已经存在，读取真实像素尺寸与 EXIF 时间。
3. 根据本文件的分类原则确定专题；地点不确定时不猜。
4. 将原图复制到相应的 `public/portfolio/<series-slug>/`。
5. 在 `src/lib/portfolio.ts` 中添加记录，并调整专题地点、年份和编辑顺序。
6. 运行 `npm run previews` 生成所有响应式预览。
7. 在真实桌面视口检查同行顶边、底边和章节节奏；在手机视口检查单列和横向溢出。
8. 完成下方全部质量检查后才能提交。

## 9. 必须通过的质量检查

```bash
npm run lint
npm test
npm run build
npm run export:github-pages
git diff --check
```

检查重点：

- 所有照片都有对应的 `1200px` 与 `1800px` 预览图。
- 所有作品只被引用一次，没有重复照片。
- 专题年份覆盖真实照片年份。
- 首页、专题索引、详情页和 404 页面均能导出。
- 新增专题时必须同步更新 Pages 导出路由、`public/sitemap.xml` 和相关测试。

## 10. GitHub Pages 发布

- 发布分支为 `main`。
- 推送后由 [`.github/workflows/pages.yml`](../.github/workflows/pages.yml) 自动部署。
- 不能只看到 `git push` 成功就宣布完成；必须确认对应 GitHub Actions 运行结果为 `success`。
- 部署完成后至少抽查受影响的公开页面，确认标题、照片和说明已经上线。
